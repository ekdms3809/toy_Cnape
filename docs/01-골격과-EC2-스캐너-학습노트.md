# 학습노트 01 — 프로젝트 골격과 EC2 보안그룹 스캐너

지금까지 만든 것: ① 프로젝트 코드 골격(공통 구조), ② 첫 번째 탐지 기능인 EC2 보안그룹 스캐너 + 테스트 9개. 이 문서는 그 안에 들어간 개념을 처음 보는 사람도 따라올 수 있게 설명한다. 모르는 단어가 나오면 그 단어가 이 프로젝트에서 왜 필요한지까지 같이 적어뒀다.

---

## 1. 전체 그림: 이 프로그램은 어떻게 돌아가나

실행 흐름은 한 줄로 이렇다.

```
python main.py --checks ec2
→ boto3 세션 생성 (AWS에 접속할 열쇠 꾸러미)
→ 선택된 스캐너 실행 (AWS API로 설정값을 읽어옴)
→ 위험하면 Finding 객체로 만들어 리스트에 담음
→ 리포터가 콘솔 요약 출력 + reports/에 JSON 저장
```

핵심 설계: **"탐지 기능이 4개든 40개든, 전부 같은 틀에 꽂히게 만든다"**. 그래서 공통 부품 3개를 먼저 만들었다.

### 1-1. Finding — 탐지 결과의 "규격 봉투" (`cspm/core/finding.py`)

모든 스캐너는 결과를 `Finding`이라는 동일한 형태로 반환한다. 왜? EC2 스캐너는 보안그룹을, S3 스캐너는 버킷을 보지만, 리포트 만드는 쪽에서는 "뭐가, 어디서, 얼마나 위험한지"만 알면 되기 때문. 규격을 통일하면 리포터·자동수정·알림 기능을 스캐너마다 다시 만들 필요가 없다.

주요 필드:

| 필드 | 의미 | 예시 |
|------|------|------|
| `check_id` | 어떤 검사인지 식별자 | `EC2-SG-001` |
| `severity` | 심각도 5단계 | `HIGH` |
| `resource_id` | 문제된 리소스 | `sg-0abc...` |
| `evidence` | 판단 근거 원본 데이터 | 매칭된 규칙, 퍼블릭 IP 목록 |
| `remediation` | 고치는 방법 | revoke CLI 명령 |
| `n2sf_area` | N2SF 통제 영역 매핑 | 분리·격리 |

파이썬 문법 포인트:

- **`@dataclass`**: 클래스에 `__init__` 같은 반복 코드를 자동 생성해주는 데코레이터. "데이터를 담는 그릇" 용도의 클래스에 쓴다.
- **`Enum`** (`Severity`): 심각도를 `"HIGH"` 같은 문자열로 아무데서나 쓰면 오타(`"Hgih"`)가 버그가 된다. Enum으로 정의하면 정해진 값만 쓸 수 있게 강제된다.

### 1-2. BaseScanner — 스캐너의 "설계 규칙" (`cspm/core/scanner.py`)

**추상 클래스(ABC)**: "이 클래스를 상속하면 반드시 `scan()`을 구현해야 한다"는 계약. 덕분에 `main.py`는 각 스캐너 내부를 몰라도 `scanner.scan()`만 호출하면 된다. 새 탐지 기능 추가 = 파일 하나 만들고 레지스트리(`scanners/__init__.py`의 `SCANNERS` 딕셔너리)에 등록. 끝.

### 1-3. boto3 세션 (`cspm/core/session.py`)

**boto3** = 파이썬용 AWS 공식 SDK. AWS 콘솔에서 클릭으로 하는 모든 일을 코드로 할 수 있다. **세션(Session)** 은 "어느 계정(프로파일)·어느 리전으로 접속할지"를 담은 객체이고, 세션에서 `client("ec2")`를 뽑으면 그 서비스의 API를 호출할 수 있다.

원칙 하나: 이 도구의 스캐너는 **읽기 전용 API만** 호출한다 (`describe_*` 계열). 설정을 바꾸는 건 자동수정 제안 기능조차 "스크립트 텍스트 생성"까지만 한다. 보안 도구가 사고 치면 안 되니까.

## 2. EC2 보안그룹이 뭔데 왜 스캔하나

**보안그룹(Security Group, SG)** = EC2 인스턴스(가상 서버) 앞에 붙는 가상 방화벽. "어떤 IP가 어떤 포트로 들어올 수 있는지"를 규칙으로 정한다.

**포트** = 서버의 문 번호. 우리가 위험하다고 보는 4개:

| 포트 | 서비스 | 왜 위험 |
|------|--------|---------|
| 22 | SSH | 서버 원격 접속. 뚫리면 서버 장악 |
| 3389 | RDP | 윈도우 원격 데스크톱. 랜섬웨어 침투 단골 경로 |
| 3306 | MySQL | DB 직접 접근. 데이터 유출 |
| 5432 | PostgreSQL | 동일 |

**`0.0.0.0/0`** = "전세계 모든 IPv4 주소". CIDR 표기법인데, `/0`은 "매칭 조건 0비트 = 아무 IP나 다 해당"이라는 뜻. IPv6 버전은 `::/0`. 즉 "SSH 포트를 0.0.0.0/0에 오픈"은 **지구상 누구나 내 서버 문을 두드릴 수 있다**는 뜻이다. 실제로 퍼블릭 IP에 22번 열어두면 몇 분 안에 전세계 봇들의 로그인 시도가 쏟아진다 (공격자들이 인터넷 전체를 상시 스캔하고 있음 — Shodan 검색해보면 체감된다).

---

## 3. 판단 기준 — 왜 이렇게 정했나 (이게 이 프로젝트의 핵심)

단순히 "22번 열려있으면 경고"로 짜면 안 되는 이유가 세 가지 있고, 각각 실제 상용/오픈소스 도구에서 근거를 가져왔다.

### 3-1. 포트는 "범위 포함"으로 판정해야 한다 (Prowler 방식)

SG 규칙은 `FromPort`~`ToPort` **범위**로 열린다. 누가 3000-4000 범위를 열면 그 안에 3306(MySQL)이 포함된다. `FromPort == 22` 같은 단순 비교는 이 케이스를 놓친다(미탐). 그래서 코드는 `from_port <= 위험포트 <= to_port` 포함 판정을 한다. 오픈소스 CSPM인 Prowler의 `check_security_group` 헬퍼가 정확히 이 방식이다 (range를 만들어 포함 여부 검사).

### 3-2. `IpProtocol: -1`은 별도로, 더 심각하게 (Prowler 방식)

SG 규칙에서 프로토콜을 `-1`로 두면 **모든 프로토콜·모든 포트** 허용이다. 이때는 `FromPort` 자체가 없어서 3-1 로직으로는 안 잡힌다. 놓치기 쉬운 케이스라 별도 check_id(`EC2-SG-002`)로 분리했고, "위험 포트 하나 오픈"보다 당연히 나쁘므로 심각도를 한 등급 올린다.

### 3-3. "설정이 위험한 것"과 "실제로 노출된 것"을 구분한다 (Wiz 철학)

여기가 상용 도구(Wiz)에서 배운 가장 중요한 개념. 22번이 열린 SG가 있어도:

- 그 SG가 **아무 데도 안 붙어있으면** → 당장 뚫릴 건 없음 (정리 안 한 설정 쓰레기)
- 붙어있는데 **프라이빗 IP뿐이면** → 인터넷에서 직접 접근 불가 (내부망 침투 후에나 문제)
- 붙어있고 **퍼블릭 IP까지 있으면** → 지금 이 순간 전세계에 노출 중

셋을 전부 같은 등급으로 알림하면 진짜 위험한 것이 소음에 묻힌다. 이걸 **alert fatigue**(경고 피로)라고 하고, 보안 운영에서 실제로 큰 문제다. Wiz가 시장을 먹은 이유 중 하나가 "설정 플래그가 아니라 인터넷→리소스 **실제 경로**가 있을 때만 심각하게 알린다"는 접근이다. 참고로 Prowler는 미연결 SG를 아예 스킵하고, AWS Trusted Advisor는 red/yellow 티어로 차등한다 — 업계 전체가 어떤 식으로든 이 구분을 한다.

그래서 우리 severity 표:

| 상태 | EC2-SG-001 (위험포트) | EC2-SG-002 (전포트) |
|------|----------------------|---------------------|
| ENI 연결 + 퍼블릭 IP | **HIGH** | **CRITICAL** |
| ENI 연결 (프라이빗) | MEDIUM | HIGH |
| 미연결 | LOW | MEDIUM |

**ENI(Elastic Network Interface)** = AWS의 가상 랜카드. SG는 사실 인스턴스가 아니라 ENI에 붙는다. 그래서 "이 SG가 실제 사용 중인가"를 확인하려면 `describe_network_interfaces`로 ENI 목록을 뒤져서 SG ID가 걸린 ENI가 있는지, 그 ENI에 퍼블릭 IP(`Association.PublicIp`)가 있는지 보면 된다. 코드의 `_map_sg_to_enis()`가 이 작업이다.

## 4. 코드 읽기 가이드 (`cspm/scanners/ec2_security_group.py`)

`scan()`의 흐름:

```
1. _map_sg_to_enis()   : 전체 ENI를 한 번 훑어서 {SG ID → ENI 목록} 딕셔너리 생성
                         (SG마다 API 부르면 느리니까 한 번에 만들어두고 조회)
2. describe_security_groups (paginator로 전체 SG 순회)
3. 각 SG마다 _check_sg():
   a. _open_sources()        : 규칙에서 0.0.0.0/0, ::/0 소스만 추출 → 없으면 통과
   b. IpProtocol == "-1"?    : 전포트 오픈 → EC2-SG-002 후보
   c. _matched_risky_ports() : TCP 범위가 위험포트 포함? → EC2-SG-001 후보
   d. _exposure()            : ENI 연결 여부 + 퍼블릭 IP 목록
   e. _severity()            : 위 표대로 등급 결정
   f. Finding 생성           : evidence에 근거 원본, remediation에 revoke 명령
```

**paginator**: AWS API는 결과가 많으면 한 번에 다 안 주고 페이지로 끊어 준다. paginator는 "다음 페이지 요청"을 자동으로 반복해주는 boto3 기능. 리소스가 몇 개 없어도 습관적으로 쓰는 게 실무 관례다 (안 쓰면 리소스 많은 계정에서 조용히 일부만 스캔하는 버그가 된다).

**SG당 Finding은 규칙별이 아니라 묶어서 1건**: 한 SG에 위험 규칙이 3개면 알림 3개가 아니라, evidence에 3개를 담은 Finding 1건. 이것도 alert fatigue 줄이기.

## 5. 테스트 — moto로 가짜 AWS 만들기 (`tests/test_ec2_security_group.py`)

**moto** = AWS API를 흉내내는 파이썬 라이브러리. `with mock_aws():` 블록 안에서는 boto3 호출이 진짜 AWS로 안 가고 메모리 속 가짜 AWS로 간다. 덕분에 요금 0원, 실제 계정 오염 없이, 원하는 위험 상황(퍼블릭 IP 인스턴스에 22 오픈 등)을 마음대로 만들어 테스트할 수 있다.

테스트 7개가 각각 검증하는 것 — 위 판단 기준과 1:1 대응된다:

| 테스트 | 검증하는 판단 기준 |
|--------|-------------------|
| 22 오픈+연결+퍼블릭 → HIGH | severity 차등 (실제 노출) |
| 3000-4000 범위에서 3306 탐지 | 범위 포함 판정 (3-1) |
| `-1` → SG-002 + CRITICAL | 전포트 분리·등급 상향 (3-2) |
| `::/0` 탐지 | IPv6도 검사 |
| `10.0.0.0/8` 소스 미탐지 | 사내망 오픈은 정상 → 오탐 방지 |
| 80 포트 미탐지 | 웹 포트는 스코프 외 → 오탐 방지 |
| 미연결 SG → LOW | severity 차등 (하이진) |

**pytest fixture**: `@pytest.fixture`가 붙은 `aws()`는 각 테스트 시작 전에 가짜 AWS + VPC + 서브넷을 만들어주는 공통 준비 코드. 테스트마다 같은 준비를 복붙하지 않기 위한 장치다.

## 6. 면접에서 나올 수 있는 질문 (스스로 답해보기)

1. "Action이 아니라 왜 FromPort/ToPort 범위로 판정했나요?" → 3-1
2. "탐지됐는데 안 위험한 경우(오탐)는 어떻게 줄였나요?" → 3-3 + 사내망/웹포트 테스트
3. "SG가 인스턴스에 붙는 게 아니라 ENI에 붙는다는 게 왜 중요한가요?" → 4장 노출 판정
4. "이 검사 로직은 어떤 표준/도구와 대응되나요?" → Security Hub EC2.19, Trusted Advisor, Prowler
5. "0.0.0.0/0으로 80/443 여는 건 왜 안 잡나요?" → 웹서버는 원래 공개가 목적. 위험은 '관리·DB 포트'의 공개. (Trusted Advisor도 25/80/443은 green 처리)
6. "N2SF의 분리·격리 통제와 어떻게 연결되나요?" → 네트워크 경계에서 인가된 대역만 접근 허용 = 망 분리·격리 원칙의 클라우드 버전
